Vantage · Internal Product Plan

Self-Driving Deal Engine

"Agent-as-deal-manager. Rep-as-executor. The agent owns the plan. The rep executes it."

Sprint baseline: 6 (shipped)
Remaining sprints: 7 – 11
Total remaining effort: ~22 dev days
North star metric: Execution Rate >60%
Date: May 2026

Vision & North Star

Vantage is a per-account AI deal engine. One agent per HubSpot deal. The agent monitors signals 24/7, maintains a living action plan, and generates prepared content for every step. The rep's interface is a queue — not a dashboard to interpret, but a sequence to execute.

This is meaningfully different from existing tools. Salesforce Einstein and Gong surface insights. Attio automates workflows. Octolane AI updates CRM fields. Vantage does something none of them do: it plans and prepares each deal's next move, continuously, and presents it as a ready-to-execute action with content already drafted.

The test for every feature: Does the rep know what to do next without thinking? Does the agent get smarter from what they did? If not, the feature is either passive information or a dead end.

Why Execution Rate, not DAR

Draft Acceptance Rate (DAR) measures "did the rep approve the agent's draft?" That is a proxy for draft quality, not for whether the platform is driving outcomes. A rep can approve every draft and still close nothing.

DAR covers step 1. Execution Rate covers steps 1–2 and forces the question: is the agent generating actions the rep actually finds useful enough to execute? Target: >60% within 8 weeks of active use.

The Self-Driving Flywheel

The flywheel only spins if every step feeds the next. Right now it stalls at step 3 — the agent generates actions, the rep executes them, and the agent never learns what happened. That's the most critical gap in the platform today.

1
Data in — HubSpot emails, notes, contacts, stage history + Fireflies transcripts + Outlook calendar + Perplexity news signals
↓
2
Agent runs — Researcher → RiskScanner → Grounding → Prioritiser → Drafter → Gap-fill → TimelineActions generated with prepared content
↓
3
Rep executes — Action Queue surfaces today's actions. Rep approves drafts, completes actions, records outcomes
↓
4
Outcome fed back — ⚠ MISSING. Completion notes → Interaction table → agent context on next run → smarter next action
↓
5
Next action generated — Agent uses outcome to plan next step. Deal advances. Cycle repeats.
Step 4 is the entire value of the platform. Without it, Vantage is a sophisticated to-do list. With it, it's a learning system that gets sharper with every deal, every rep, every outcome.

Reply rate tracking (the real DAR)
Of emails the agent drafted, approved, and sent — what % got a reply? This is derivable from HubSpot email engagement data already being synced. Reply rate is the outcome metric DAR is a proxy for. Measure both, report both.

Execution rate dashboard (per-rep, per-week)
Completed actions / generated actions, per rep, per week. This is the north star metric. If below 30%, the agent is generating too many wrong actions. If above 70%, the platform is running the rep's day. The data is in the timeline_actions table — needs a rollup endpoint and a chart.

Win/Loss capture flow + analytics
When a deal closes Won or Lost, capture the reason with a structured prompt (3–4 categories + free text). Over 376 deals, this becomes the most valuable training data the agent will ever have: "We lose 60% of competitive deals where Voxel is mentioned." Currently nothing is captured at deal close.

Pipeline movement analytics
How many deals advanced stages this month vs. last? Which stage is the biggest bottleneck? The ForecastSnapshot table already exists and can answer this with a simple aggregation. This is the #1 question in every pipeline review meeting.

We track LLM cost obsessively ($0.22/run) but never connect it to outcomes. "~$2,500/month in LLM costs → 14 deals advanced → $178/deal advanced." This is the number that justifies the platform to Vishnu and eventually to paying customers. Computable from existing cost + velocity data.

Execution Rate ★
—
Target: >60% by Week 8

Completed actions / generated actions. The single number that tells you if the agent is running the rep's day or just adding noise.

Reply Rate
—
Target: >30%

Approved emails that received a reply. The outcome metric DAR has always been a proxy for.

Target: >60%

Kept as a draft quality signal. If DAR is high but Reply Rate is low, the drafts are approved but ineffective.

Design Principles

Three questions to ask of every feature before building. If you can't answer yes to both of the first two, the feature is either passive information or a dead end.

Does the rep know what to do next without thinking?
The platform should eliminate decision fatigue, not add to it. Every view should have one obvious primary action. If a rep opens Watchtower and has to decide what to do, the feature isn't done.
Does the agent get smarter from what the rep did?
Every rep action — completion, skip, decline, edit, outcome note — is training data. If an action disappears without leaving a trace the agent can learn from, we've broken the flywheel. No silent state changes.
Is the rep doing less work than before Vantage?
The test for self-driving. If a feature adds configuration, navigation, or decision-making without removing more of each in return, it's complexity not value. Every screen should save more time than it takes.
The 50-action problem is a design smell, not a data problem. When the queue shows 50 actions today, the agent is treating all 376 deals equally. Urgency, deal value, and close date proximity need to collapse into a composite focus score. The rep sees 7 things. The agent has done its job.
